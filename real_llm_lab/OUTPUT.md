```text
  计时方式：每个配置先预热 1 次，再取 2 次中的最好成绩（best-of-2）

  -------------------------------------------------------------------------
       16 |      562.7 ms |       257.3 ms | x  2.19 | x  21.0 |    186.6 tok/s

  加速比 = naive / cached（同一个 prompt、同样生成这么多 token）
  理论比 = 两种实现各自的「token 前向次数」之比，也就是纯算法的上限
  -> 实测加速比只有理论上限的一小部分，原因见最后的讨论

--- 3. 单步前向延迟：一次全量重算 vs 一次 cache decode ---
  计时方式：预热 1 次 + best-of-3

  context |     全量前向 T=ctx |    折合每 token | cached decode T=1 |      单步加速比 |   prefill 参考
  ---------------------------------------------------------------------------------------
       16 |         14.5 ms |       0.91 ms |            7.41 ms | x      2.0 |       14.5 ms
       64 |         22.5 ms |       0.35 ms |            7.34 ms | x      3.1 |       22.8 ms
      256 |         63.3 ms |       0.25 ms |            7.65 ms | x      8.3 |       63.6 ms
      512 |        131.0 ms |       0.26 ms |            8.21 ms | x     16.0 |      132.8 ms

  怎么读这张表：
    「全量前向 T=ctx」这一列随 context 变大而变长——
      因为注意力是 O(T^2)：每个位置都要和前面所有位置算相似度，
      所以 naive 生成到后面，每一步都在变慢。
    「cached decode T=1」这一列几乎是平的——
      因为每步只算 1 个新 token 的 q/k/v，历史 K、V 直接从缓存里切出来，
      注意力对 T 个位置做加权是 O(T)，T 从 16 长到 512 只多一点点。
    「折合每 token」是关键：它在大上下文时趋近于 ~0.26 ms/token，
      而一次 T=1 的调用却要 ~8.21 ms——两者差 31 倍，这就是固定开销。

  把数字拆开看（context=512 这组）：
    在大上下文下多处理 1 个 token 的边际成本 ≈ 0.26 ms
    而一次独立的 T=1 调用要 8.21 ms
    => 每次调用有约 7.9 ms 的固定开销
    这部分主要是「把 475 MiB 权重从内存读一遍」（等效带宽 61 GB/s）+ Python 层算子调度。
    KV cache 能省掉重复的矩阵乘，但省不掉这 7.9 ms。

--- 4. KV cache 到底占多少内存 ---
  公式: 2 * n_layer * B * T_max * C * 4 字节
      = 2 * 12 * 1 * 1024 * 768 * 4
      = 75,497,472 字节 = 72.0 MiB = 75.5 MB
  KVCache(...).memory_bytes() = 75,497,472 字节 = 72.0 MiB

  对照：模型权重 124,439,808 个参数 * 4 字节 = 475 MiB
        缓存 / 权重 = 15.2%
  注意：这里是按 T_max=1024（block_size）**预分配**的，
        只用到 512 个位置的话实际只需要 36.0 MiB。
        长度换算：每多 1 个 token 的上下文，缓存多 72 KiB。
  [OK] 公式与实际分配一致

==============================================================================
1) 正确性：两种实现逐 token 完全相同。fp32 下 16 步 logits 相对差 2.4e-06、绝对差 7.0e-04（logits 量级 319）；

   所以在 CPU fp32 上加速比只能到几倍，而不是几十倍。
4) 单步：全量前向随 context 线性上升（15 -> 131 ms），
   cached decode 基本恒定（7.4 ~ 8.2 ms），这就是长上下文生成时缓存的价值。
5) 缓存大小 72.0 MiB（权重 475 MiB 的 15%），按 T_max 预分配，随层数/上下文线性增长。

一句话：KV cache 让「每步的计算量」不再随上下文增长（步骤 3 的平线），
但每步的固定开销它省不掉，所以在小模型/短上下文/CPU 上，
端到端加速比是「几倍」这个量级，而不是复杂度公式给出的「几十倍」。

思考题：
  1. 如果把 batch 从 1 改成 8，cached 的固定开销会被摊薄，加速比会怎么变？
  2. 为什么 decode 时慢的其实是「读权重」（内存带宽），而不是「算数」？
     这对量化（fp16/int8）意味着什么？
  3. 换成 GPU，为什么加速比会比 CPU 上大得多？（固定开销占比不同）
```

## 实验 4：因果掩码 + 困惑度 + 训练期对照

掩码反例、bits/char、无掩码训练

```text
$ .venv/bin/python real_llm_lab/exp4_mask_ppl.py

======================================================================
0. 加载真实 GPT-2 small 权重
======================================================================
参数量 = 124,439,808
配置   = GPT2Config(n_layer=12, n_head=12, n_embd=768, block_size=1024, vocab_size=50257, layer_norm_eps=1e-05)

======================================================================
1. 因果掩码反例：让模型「看到未来」会怎样？
======================================================================
英文新闻段落：1092 个字符 -> 235 个 BPE token
开头 80 个字符：'Astronomers said on Tuesday that a new survey of the southern sky had revealed\nm' ...

同一段文字、同一份权重，只改一个开关 causal：
  causal=True  （正常，位置 t 只能看 0..t）: loss = 3.2987   perplexity = 27.1
  causal=False （去掉掩码，位置 t 能看到整个序列）: loss = 5.9697   perplexity = 391.4
  -> loss 反而上升了 2.6710，困惑度变成原来的 14.5 倍

结果可能和直觉相反：不是「能看到未来 -> 更容易抄答案 -> loss 更低」吗？
对**已经训练好、权重固定**的 GPT-2 来说，去掉掩码只会把它弄坏：

  1) 这 124M 个参数是针对「因果注意力」训练出来的。每个头学到的东西
     （比如 exp2 里那个复制头：把注意力放到 i-period+1 的位置）
     都建立在「只能看左边」这个前提上。
  2) 去掉掩码后，位置 t 的输入里混进了右边的 token，隐藏状态立刻偏离
     训练时见过的分布，144 个头的行为全部改变，预测自然变差。
  3) 所以「同一份权重 + 不同掩码」= 一个不同的函数。掩码不是装饰，
     它是模型定义的一部分（就是你 step04 里写的那行 masked_fill）。

那「训练时不加掩码会导致 loss 异常低」又是怎么回事？
  那是**从随机初始化开始训练**的情况：没有掩码时，模型会学会直接把
  位置 t+1 的 token 信息搬到位置 t（答案就在眼前），训练 loss 可以降到很低；
  但生成时它只能看到前缀，作弊手段失效，效果立刻崩掉。
  两件事不矛盾：一个说的是「固定权重的预训练模型被改坏」，
  另一个说的是「训练时学会了作弊」。想亲手验证后者，见 README 的延伸练习。


======================================================================
2. 随机初始化对照：真权重 vs 随机权重

构造一个 12 层 / 12 头 / 768 维的同结构模型，权重全部随机……
随机权重（GPT-2 官方初始化 N(0,0.02)）: loss = 10.9578   perplexity = 57,402.8   (1.2s)
参考：完全均匀地瞎猜 loss = ln(50257) = 10.8249，perplexity = 50257

真实预训练权重 loss = 3.2987，随机权重 loss = 10.9578，差 7.66 nats/token
用随机权重时，模型对「下一个词」几乎没有任何偏好，所以 loss 就停在均匀分布附近；
真实权重把 loss 压到 3 左右，说明它确实从海量文本里学到了语言规律——
这些数字（124M 个浮点数）不是结构给的，是训练出来的。

顺便一提：如果直接用 PyTorch 默认初始化（nn.Embedding 是 N(0,1)），
loss = 484.9（0.5s，远超 10.83）。
那不是「没学过」，而是初始化尺度不对：嵌入大了 50 倍，logits 爆炸，
softmax 变成几乎 one-hot 的乱猜。所以上面的随机权重按官方初始化 N(0,0.02)。

3. 困惑度表格：GPT-2 眼里的四种文本

  English (news)     1092     234      0.21   3.2987         27.1       1.02
  Chinese (text)      149     313      2.10   2.8272         16.9       8.57

怎么读这张表（这里有一个新手最容易踩的坑）：

  1) 先看 per-token perplexity：中文 16.9 反而比英文 27.1 低！
     直觉会说「中文更难」才对。问题在于「token」不是公平的单位：
     GPT-2 是字节级 BPE，一个汉字要 2.11 个 token；
     而一个汉字的 UTF-8 字节序列本身高度可预测（第一个字节基本确定了后面几个），
     所以「每个 token」看起来很便宜。

  2) 中图把单位换成「每个字符花多少 bit」（bits/char）：
     英文 1.02，中文 8.57，Python 1.92。
     这才是跨分词器可比的数字：同一段中文，GPT-2 每个字符要多花
     8.4 倍的代价——符合「它不是为中文训练的」。

  3) 结论：**不同分词器的 perplexity 不能直接比**。
     比较模型能力要用 bits/char、bits/byte 这类和分词无关的单位，
     或者至少保证两边用同一个分词器。

  4) 同样的坑再来一次：Python 代码每 token 的 ppl 只有 14.4，
     但按字符算 1.92 bit，反而比英文新闻（1.02）贵。
     因为代码的 token 更短（0.50 tok/char 左右，缩进、标点都被单独切出来），
     「per-token 更低」不代表「按字符更便宜」。

  5) 随机 id 的 ppl 约 259,839，比「均匀瞎猜」的 50257 还高：
     模型被训练得偏向自然语言，随机 id 反而落在分布外，属于最坏情况。
```
